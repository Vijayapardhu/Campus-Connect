The problem

You have emailed yourself a link. Everyone has.

You are on the lab machine and you need something from your own laptop. So you message it to yourself, or type out a forty-character URL by hand and get one character wrong. Every workaround sends your clipboard to a server that has no business seeing it.

Emailing it to yourself

  • Your clipboard goes to someone else's server
  • Needs an internet connection
  • Log in, compose, send, open, copy — every single time
  • Images and screenshots are even more painful

Shared Clipboard

  • Stays on your own network
  • Works on WiFi with no internet
  • Ctrl+C here, Ctrl+V there. That is the whole workflow
  • Text and images, with history you can go back through

How it works

Three steps, then you forget it is there

1. Make a room

A room is the privacy boundary — nothing is shared outside the one you have selected. Public for a lab, private with a password for anything that matters.

2. Let the other device in

Rooms on the network show up automatically. Enter the six-character code and the password, and the owner approves you. Private rooms never admit anyone silently.

3. Copy and paste

That is genuinely it. Copy on one machine, Ctrl+V on the other. Everything collects in the room's history so you can go back to what you copied an hour ago.

Chat, per room

Sometimes you need a sentence, not a snippet. Chat is scoped to the room and encrypted with it.

You stay in control

Approve or decline requests, remove a member at any time, or close the room for everyone. Removal takes effect immediately.

Comfortable to look at

Light and dark themes, adjustable text size, and a font picker that reads the fonts actually installed on your machine.

Security

"Encrypted" gets claimed a lot. Here is exactly what happens.

Everything security-related uses the Node standard library — no crypto dependency to audit or trust. You can read all of it in an afternoon. 

Your password ──scrypt(N=32768)──▶ 32-byte room key
      │                                    │
      │  never leaves this device          ▼
      ▼                        AES-256-GCM(key, payload)
 ✗ never transmitted                     │
                                          ▼
                        { iv, ciphertext, auth tag } ──▶ network
1
The password is never sent It only ever feeds scrypt, locally. To join, your device seals a known phrase with the derived key and sends that. Only someone who knows the password could produce something the owner can open.
2
Four checks before anything is applied A packet is acted on only when the room exists here, you are an accepted member, the sender is an accepted member, and the payload actually decrypts. Anything else is dropped.
3
Tampering is detected, not just decryption failure GCM's authentication tag means a modified packet is rejected outright instead of quietly producing garbage.
4
Proofs cannot be replayed Each proof is bound to its room's id, so one captured from one room is useless at another.
5
Removal is immediate The room owner is the single source of truth for the roster. Remove someone and every device updates — they cannot read anything sent afterwards.

And what it does not protect against

Overclaiming is worse than a smaller claim, so these are written down plainly rather than buried:

  • Room names and owner names are public — adverts are broadcast so devices can find rooms. Rosters, join codes and content are not.
  • Traffic analysis: an observer can see that a room is busy and roughly how large its messages are.
  • Derived keys are cached on disk so you do not retype the password every launch. Anyone with access to your user profile can read them.
  • A public room with no password is plain text. That is what it means, and the app labels it "Not encrypted".
  • Physical or administrator access to a machine defeats all of it.

The full model is in SECURITY.md. If you can break one of the five claims above, please report it.

Under the hood

Boring, readable technology

Every choice here was made so that someone can clone the repo and understand the whole thing. There is no message broker, no backend, and no cryptography dependency.

Electron 35One codebase, three desktop platforms, real clipboard access
TypeScript 5.8Strict mode — a wire protocol is easy to get wrong
React 19The whole interface is state-driven
Vite 6Fast dev server, small production build
Node dgramUDP broadcast on the LAN. No server, no broker
Node cryptoscrypt and AES-256-GCM from the standard library
electron-builderNSIS, DMG and AppImage from one config

Try it

Running from source takes a minute

You need Node.js 20 or newer. That is the only prerequisite.

git clone https://github.com/Vijayapardhu/Clipboard.git
cd Clipboard && npm install
npm run dev

Run npm test for the 29 assertions covering key derivation, envelope tampering, IV reuse, proof forgery and the membership rules. They run in plain Node — the security modules import nothing from Electron.
